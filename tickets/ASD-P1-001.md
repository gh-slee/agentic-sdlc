# ASD-P1-001: Decide whether the ticket workflow ships to adopting projects

## Goal

The ticket kit now governs this repository, but the framework itself only describes logical claims and handoffs (core/lifecycle.md, roles/coordinator.md, templates/handoff.md) and ADR-001 rules out locks and orchestration in the framework. The owner decides whether adopters get the ticket workflow as an optional adapter.

## Acceptance criteria

- [ ] Owner decision recorded in this ticket and, if accepted, as an ADR.
- [ ] Follow-up implementation ticket ASD-P1-002 updated to match the decision.

## Plan

- [ ] Owner chooses an option below.
- [ ] Record the decision and update ASD-P1-002.

## Decisions needed

- Option A (recommended): ship it as an optional adapter under `integrations/` with a mapping from ticket statuses to the lifecycle Execution states and from Handoff to templates/handoff.md. Core stays tool-neutral and ADR-001 is unchanged for core.
- Option B: keep the ticket workflow repository-internal only; adopters keep the logical model.
- Option C: make it part of core. Not recommended: it would add a cross-process lock mechanism to core, which ADR-001 deliberately excluded.

## Handoff

- State: Waiting for the owner.
- Next step: Owner picks option A, B or C and records `gate_approval`.
- Verify: Not applicable.
- Gotchas: Ticket statuses (`in_progress`, `in_review`, `done`) are coarser than the lifecycle's separate review/QA/merge dimensions; a mapping must not imply approval.
- Open questions: Which option.
